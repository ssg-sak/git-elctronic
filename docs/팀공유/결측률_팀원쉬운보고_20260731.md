## 3. “고장”이 아닌 빈칸

아래는 **채우면 안 되는** 쪽에 가깝습니다.

| 빈 컬럼 | 왜 비나 | 잘못 읽으면 |
|---|---|---|
| `eta_minutes` | ①이 안 채움 (BE 예약) | “데이터 없다”고 폐기 |
| `usage_level` 등 | 이력 원천 커버리지 낮음 | 조인 버그로 오해 |
| `nearest_incident_m` | 근처 돌발 없음 | “항상 위험/안전” 단정 |
| parking realtime / 1h | realtime 붙은 소만 (~428) | 전 소 주차 점수로 오해 |
| link 35% | 거리 게이트(≤400m) | 소통 데이터 전체 실패로 오해 |

## 4. 그럼 무엇을 해결하나?

### 팀이 같이 할 일 (가장 중요)

**Null 계약 지키기**

| 규칙 | 설명 |
|---|---|
| 미관측 ≠ 사용 불가 | 상태 없다고 후보에서 바로 빼지 말 것 |
| ETA 빈칸 | ① 자료만 보고 이동시간 없다고 하지 말 것 → BE |
| 주차·돌발·요금 null | 점수 감점/탈락에 쓰지 말 것 (합의 전) |
| 빈칸을 평균으로 채우기 | **금지** |

### ①이 선택적으로 할 일

| 항목 | 내용 |
|---|---|
| 요금 ~3% 미매칭 | 차지인 등 **이름 별칭** 보강 (되면 좋음, 필수는 아님) |
| 주차 | **14일** realtime+상태 쌓인 뒤 점수 게이트 재실행 |

### ②·BE가 할 일

| 담당 | 내용 |
|---|---|
| **BE** | ETA·요금 응답에서 null 처리, 화면 문구 |
| **②** | 빈 보조신호를 “나쁜 충전소”로 해석하지 않기 |

---

## 5. 복붙용 한 단락 (톡/회의)

> 결측률 점검 결과, ID·좌표·공용여부·상태 핵심은 거의 안 비고,  
> ETA 100%·이용이력·돌발·주차 realtime 높은 결측은 **의도적 null이거나 원천 커버리지**다.  
> 해결할 것은 빈칸 메우기가 아니라 **null 계약**(미관측 탈락 금지, ETA는 BE, 주차·요금 점수 미반영).  
> 요금은 운영사 기준으로 이미 **97%** 힌트 가능.
