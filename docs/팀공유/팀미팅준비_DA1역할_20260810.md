## 1. 프로젝트 기획에서의 데이터 역할

EV SafeCharge의 핵심은 “가까운 충전소”가 아니라 **도착했을 때 실제로 충전할 가능성이 높은 충전소**를 고르는 것이다.  
이를 위해서는 실시간에 가까운 충전기 상태, 그 상태가 언제 갱신됐는지(신선도), 시간대에 따른 가용 패턴, 그리고 학습·규칙이 먹을 수 있는 표 형태 입력이 필요하다.

공공 충전기 상태는 갱신 지연, 페이지 수집 중 중복, 결측·미관측이 섞일 수 있다. 원문을 그대로 쓰면 “지금 비어 있다”는 판단을 잘못 내릴 수 있다.  
①의 역할은 그 원천을 **품질 게이트와 기준시각이 붙은 현황·시계열·지표**로 정리해, ②·백엔드·프론트가 쓰는 입력 층을 만드는 것이다.

구체적으로 ①이 만든 것은 다음이다.

- **현재표**: 충전소 1행, 기준시각(as_of)이 명시된 “지금” 스냅샷  
- **시간표**: 충전소 × 시각 패널, 시간대·패턴·학습용 시계열  
- **라벨·피처 계약·한계 문서**: 모델·규칙이 먹을 입력의 정의와 HOLD 사유  

추천 점수, Top-N, REST 응답, 앱 화면은 ① 범위가 아니다.  
학습에 쓴 이동시간(ETA)은 **동대구역 고정 출발**이며, 서비스 서빙의 최종 후보는 **사용자 위치 기준 TMAP**이어야 한다.

## 2. 데이터 수집 (공공·외부)

### 2.1 사용 데이터

주력은 한국환경공단 EvCharger(data.go.kr)의 충전기 정보와 **실시간 상태**다. 상태는 Lightsail에서 수 분 주기로 수집한 뒤 PC로 pull·아카이브했다.

보조로 대구 교통 소통·UTIC 돌발, TMAP 경로(학습용), Team5 등 주차, TourAPI 등 공간 조인 자료를 붙였다.  
다만 주차 realtime 커버는 얇고(예: 428 수준 한계), UTIC는 Lightsail IP 거부로 신규 적재가 어려워 **기존 조인을 유지하고 한계를 문서화**했다. 이들은 MVP 주력 점수에 넣지 않고 보조로만 둔다.

### 2.2 수집 규모 (최종 컷)

| 항목 | 값 |
|---|---|
| 수집 구간 | 2026-07-17 ~ 2026-08-09 07:23 |
| 상태 스냅샷 | 약 **2,960**장 |
| 최종 pull | `from_lightsail_20260809_072742` (+status 120 / +traffic 160) |
| 현재표 as_of | `2026-08-09T07:23:21+09:00` |

EvCharger 계열은 일 트래픽 한도가 있어, 개발 중 불필요한 반복 호출을 피하고 수집분을 재사용했다.

### 2.3 수집 단계의 주요 이슈

페이지 단위로 상태를 받다 보면 같은 스냅샷 안에 `(statId, chgerId)` 중복이 생긴다. 로더는 원본 CSV를 바꾸지 않고, 읽을 때 최신 `statUpdDt`만 남긴다.  
UTIC·주차는 커버·수집 제약 때문에 주력 입력에서 제외하거나 HOLD로 남겼다. 상세 키·엔드포인트는 `apps/data-pipeline/AGENTS.md`를 따른다.

## 3. 데이터 분석·전처리

### 3.1 전처리 파이프라인 (무엇을 어떻게 바꿨는지)

수집 원본(스냅샷 CSV)은 그대로 두고, 아래 순서로 **읽는 쪽·산출 표**만 만든다.

**① 스냅 로드 + 중복 제거** (`load_snapshots.py`)  
한 스냅 안에 같은 `(statId, chgerId)`가 페이지 경계로 두 줄 들어오면, `statUpdDt`가 더 최근인 행만 남긴다.

**② 상태코드 매핑** (`cleansing.py` `STAT_MAP` · 정본 `docs/data/스키마/상태코드_매핑.md`)  
EvCharger 원천 컬럼 `stat`은 숫자 코드다. 서비스·피처에서는 이 숫자를 쓰지 않고, 아래 **표준 5값**으로 바꾼다. 원천 숫자는 `stat` / `stat_raw`에 보존한다.

| 원천 `stat` | API 의미 | 표준(한글) | 표준 코드 |
|---|---|---|---|
| `1` | 통신이상 | 미확인 | `UNKNOWN` |
| `2` | 충전대기 | 사용 가능 | `AVAILABLE` |
| `3` | 충전중 | 사용 중 | `IN_USE` / `CHARGING` |
| `4` | 운영중지 | 고장 | `OUT_OF_ORDER` |
| `5` | 점검중 | 점검 | `UNDER_INSPECTION` |
| `9` · 없음 · 미매핑 | 상태미확인·미관측 | 미확인 | `UNKNOWN` |

여기서 “매핑”이란 **충전기 상태 숫자 → 위 표준 라벨**이다. 충전기 타입(`chgerType` 01~11) 매핑은 별도이며, 가용률 분모에는 넣지 않는다.

**③ 시간 패널 (gap-safe)** (`build_panel.py`)  
충전기×시각 wide 패널을 만든 뒤, 스냅 간격이 **25분 초과**면 `segment`를 끊고 그 구간 안에서만 forward-fill 한다. 공백 이후에도 예전 `AVAILABLE`을 끌어오지 않는다.

**④ 충전소 집계** (`build_d2_panel.py` → 시간표)  
충전기 단위를 충전소(`statId`)로 묶는다.

- `available_count` = 표준 `AVAILABLE`(`stat==2`) 대수  
- `in_use_count` = 표준 `IN_USE`(`stat==3`) 대수  
- **가용률** = `available / (available + in_use)` · 미관측·고장·점검은 분모 제외  
- `has_confirmed_available` = 사용 가능 ≥ 1  

미관측(`UNKNOWN`/조인 실패)은 **고장이 아니다**. `available_count=0`으로 강제하지 않는다.

**⑤ 현재표 (as_of)** (`build_d1_snapshot.py`)  
기준시각 `as_of` 이전의 최신 상태만 조인한다(`statUpdDt ≤ as_of`).  
충전소 단위로 가용·대수 집계 후, `statUpdDt` 경과로 신선도 등급(HIGH≤5분 / NORMAL≤15분 / CHECK)을 붙인다.  
좌표는 `coordinate_quality_flag==OK` → `coord_ok`. 이용제한은 충전기 중 하나라도 `limitYn=Y`면 `access_restricted`.

### 3.2 분석 결과 요지

패널 가용률은 **낮·이른 아침에 높고 저녁(특히 18~19시 전후)에 낮은** 일중 패턴을 보인다. 거리순만으로 추천하면 저녁대 실패 위험을 설명하기 어렵다.  
신선도(수집 시각 대비 상태 갱신 경과)는 팀 규칙과 동일하게 5분 이내 HIGH, 15분 이내 NORMAL, 그 이상 CHECK로 두었다. 관측 행 기준으로는 HIGH·NORMAL이 대부분이며, 오래된 상태를 “지금 가능”처럼 쓰면 안 된다는 전제가 데이터로 지지된다.

충전기 1대뿐인 충전소는 실패 위험이 커질 수 있어, 대수·가용을 같이 본다.  
품질 validate는 **FAIL 0**이다. 수집 종료 후 모니터의 age FAIL은 컷 이후라 정상이며, 리포트에는 as_of를 명시한다.

usage 희소·주차 커버 부족 피처는 MVP 주력에서 제외(HOLD)했다. 과적합·과해석을 막기 위한 결정이다.
