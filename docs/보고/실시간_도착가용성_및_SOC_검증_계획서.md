## 1. 문제 정의

현재 가용한 충전소를 추천해도 사용자가 이동하는 동안 다음 일이 발생할 수 있다.

```text
추천 시점: 충전 가능
        ↓ 이동 시간
도착 시점: 다른 차량이 점유하여 충전 불가
```

따라서 서비스의 핵심 판단 단위는 `현재 가용성`이 아니라 다음으로 정의한다.

> **사용자의 현재 SOC와 ETA를 고려했을 때, 도착 시점에 충전할 수 있을 가능성이 높은 후보를 선택하고, 이동 중 상태가 바뀌면 다시 추천한다.**

예약·점유 잠금 기능이 없으므로 충전 성공을 보장한다고 표현하지 않는다. 검증 목표는 `도착 시점 가용성`을 높이고, 불가해졌을 때 빠르게 대체 후보로 전환하는 것이다.

## 2. 검증 질문과 성공 기준

### 2.1 반드시 답해야 하는 질문

1. 현재 가용한 충전소가 ETA 후에도 가용할 가능성이 얼마나 되는가?
2. 상태 데이터가 오래될수록 도착 시점 실패율이 증가하는가?
3. 현재 SOC가 낮을 때 안전하게 도달할 수 있는 후보가 충분히 남는가?
4. 추천 후 충전소 상태가 바뀌면 대체 후보가 존재하는가?
5. 실시간 재조회와 재랭킹에 필요한 데이터가 정해진 시간 안에 도착하는가?

### 2.2 1차 성공 기준

| 영역 | 지표 | 기준 방향 |
|---|---|---|
| 도착 가용성 | `arrival_available_rate` | 거리순 기준선보다 높음 |
| 안전 도착 | `safe_arrival_rate` | SOC 위험 후보의 누락을 최소화 |
| 재추천 | `fallback_candidate_coverage` | 상태 변경 시 대체 후보가 충분함 |
| 신선도 | `status_age_at_recommendation` | 최신 데이터일수록 도착 실패율이 낮아야 함 |
| 운영성 | `recommendation_change_rate` | 지나치게 잦은 변경은 경고·재조회 정책으로 제어 |
| 품질 | 중복·누락·시간 역전·미래정보 누출 | 0건 또는 사전 합의된 허용률 |

수치 목표값은 AWS 최신 데이터로 기준선을 산출한 뒤 DA①·DA②·백엔드가 합의한다. 근거 없이 임의의 정확도나 성공률을 보장하지 않는다.

## 3. DA①이 제공할 데이터

### 3.1 추천 입력 스냅샷

행 단위는 `충전소 1개 × 추천 기준시각(as_of)`으로 통일한다.

```text
station_id
as_of
status_observed_at
status_age_minutes
available_count
operating_count
confirmed_available
observation_coverage
data_quality_flags
current_soc_percent
arrival_soc_percent
soc_safety_margin
soc_risk_level
eta_minutes
```

`current_soc_percent`는 서버가 임의로 추정하지 않는다. 사용자가 입력하거나 차량 연동이 제공한 값을 요청 시점의 입력으로 결합한다.

### 3.2 상태 변화 이벤트

AWS 상태 스냅샷에서 충전소별로 다음 이벤트를 파생한다.

```text
station_id
event_at
previous_available_count
new_available_count
availability_changed
state_transition
source_snapshot_id
```

이 이벤트가 있어야 “추천 후 도착 전 상태 변경”을 재생하고 측정할 수 있다.

### 3.3 품질 플래그

```text
FRESH
AGING
CHECK_REQUIRED
UNOBSERVED
DUPLICATE_REMOVED
COORDINATE_EXCLUDED
ETA_UNAVAILABLE
SOC_FALLBACK
```

품질 플래그는 점수에 섞어 숨기지 않고 DA②와 백엔드가 필터·감점·화면 경고에 활용할 수 있도록 별도 필드로 전달한다.

## 4. SOC 검증 계획

### 4.1 계산 기준

```text
소모 전력(kWh) = 이동 거리(km) ÷ 전비(km/kWh)
소모 SOC(%) = 소모 전력 ÷ 배터리 용량 × 100
도착 SOC(%) = 현재 SOC - 소모 SOC
```

현재 SOC 계산은 방전 방지용 보수적 기준선으로 사용한다. SOC 실증 보고서의 단일 트립 결과는 기준선 검증의 출발점이며, 일반 차량 전체에 대한 성능 보증으로 해석하지 않는다.

### 4.2 필수 검증

- 거리·배터리 용량·SOC 단위와 범위 검사
- 차량 마스터 중복·결측·비정상 제원 검사
- 차량별·거리별·SOC 구간별 도착 SOC 계산
- 실제보다 낙관적인 예측 비율 측정
- 차량 미등록 시 fallback 적용 여부
- SOC 10% 하드필터 전후 후보 수와 안전 후보 보존율 비교

### 4.3 추가 실증

가능한 실주행 BMS 데이터에서 여러 트립·차종·도로 조건으로 실제 SOC 감소량과 비교한다. 표본이 부족하면 “검증 불가”로 남기고, 시나리오 분석과 실증 결과를 섞지 않는다.

## 5. 도착 시점 가용성 Replay

### 5.1 기본 절차

```text
과거 시각 t0의 충전소 상태 선택
        ↓
사용자 위치·차량·SOC·목적지·ETA 결합
        ↓
t0 시점 추천 후보 생성
        ↓
t0 + ETA 시점의 실제 상태 조회
        ↓
도착 시 가용성·SOC 안전성·대체 후보 평가
```

### 5.2 비교 기준선

- 거리순 추천
- 현재 `confirmed_available` 순 추천
- SOC 하드필터만 적용한 규칙
- 상태 신선도와 ETA를 함께 적용한 규칙
- DA② 최종 점수

최종 모델은 반드시 단순 기준선보다 나은지 비교한다.

### 5.3 산출물

- `arrival_availability_replay.csv`
- `arrival_availability_summary.json`
- 시간대·요일·ETA 구간별 성능표
- 추천 시점 상태와 도착 시점 상태가 달라진 사례 목록
- 상태 변경 후 fallback 후보 존재 여부

## 6. 실시간 재추천 운영 흐름

실시간성은 수집 주기만으로 해결되지 않는다. 다음 세 단계가 필요하다.

```text
1. 추천 직전 충전소 상태 재조회
2. 이동 중 상태 변경·ETA 변화 감지
3. 위험 후보가 되면 후보 재랭킹 및 대체 추천
```

재추천 트리거 후보:

- `available_count`가 1 이하로 감소
- 추천 충전소가 `CHECK_REQUIRED`가 됨
- ETA가 합의된 임계값 이상 변함
- 예상 도착 SOC가 위험 구간으로 진입
- 추천 기준시각 대비 상태 데이터가 stale 됨

DA①은 트리거용 데이터와 기준을 정의하고, 백엔드는 실제 재조회·재랭킹·사용자 알림을 구현한다.

## 8. 단계별 실행 순서

### Phase 1 — 데이터 계약 고정

- `as_of`, `status_observed_at`, `status_age_minutes` 정의

### Phase 2 — 기준선과 품질 게이트

- 현재 AWS 산출물로 중복·결측·시간 정합성 점검

- 거리순·현재 가용순 기준선 생성
- D1/D2와 추천 입력 스냅샷 연결

### Phase 3 — 도착 시점 Replay

- 실제 상태 이력에서 `t0`와 `t0+ETA` 쌍 생성
- 상태 변경·미관측·대체 후보 사례 분류
- SOC 구간·ETA 구간·시간대별 결과 산출

### Phase 4 — 재추천 연동 검증

- 상태 변경 이벤트를 재추천 트리거로 변환

- 후보 교체 지연시간 측정
- 최종 서비스 시나리오 테스트

## 9. 완료 게이트

다음 조건을 충족하기 전에는 “도착 시 충전 가능성이 높다”는 서비스 핵심 문구를 확정하지 않는다.

- 추천 입력의 기준시각과 출처가 모든 후보에 존재한다.
- 미래 시점 정보가 추천 입력에 누출되지 않는다.
- SOC 계산과 차량 fallback 테스트가 통과한다.
- 도착 시점 가용성 replay가 기준선과 비교 가능하다.
- 상태 변경 시 대체 후보 커버리지가 측정된다.
- 상태 미관측·stale·SOC fallback이 사용자와 DA②에 구분되어 전달된다.
- AWS 최신 데이터 기준으로 재현 가능한 실행 명령과 결과 파일이 남는다.

## 10. 당장 할 일

1. AWS 최신 상태 이력에서 `station_id + observed_at` 기준 중복과 시간 정합성을 확인한다.
2. 차량 마스터·SOC 계산 불변식 테스트를 추가한다.
3. `t0 → t0+ETA` 도착 시점 가용성 replay의 최소 샘플을 만든다.
4. `arrival_available_rate`, `safe_arrival_rate`, `fallback_candidate_coverage` 기준선을 계산한다.
5. 결과를 DA②와 백엔드에 공유하고 점수·재조회 계약을 합의한다.

이 계획의 목표는 “충전 가능성을 보장한다”가 아니라, **추천 시점의 정보가 도착 시점 판단에 얼마나 유효했는지를 데이터로 증명하고, 틀릴 때 빠르게 바꾸는 구조를 만드는 것**이다.
