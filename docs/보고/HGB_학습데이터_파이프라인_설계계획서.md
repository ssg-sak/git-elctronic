## 1. 결론

HistGradientBoosting만을 위한 별도 수집 파이프라인은 만들지 않는다. 현재 AWS 상태 수집과 DA① 정제·패널을 재사용하고, 마지막에 **모델 공용 학습 마트 생성 단계**를 추가한다.

```text
AWS 상태 수집
→ 원본 품질검사·중복 제거
→ as-of 상태 정합
→ 충전소 시계열 패널
→ 과거 정보만 사용한 피처 생성
→ t0+horizon 관측 라벨 결합
→ station_horizon_training_v1
→ DA② 모델 학습·평가·서빙
```

이 구조는 HistGradientBoosting, GradientBoosting, LogisticRegression 등 모델이 바뀌어도 동일하게 사용한다.

## 2. 현재 자산과 부족한 부분

### 2.1 재사용할 자산

- AWS 충전기 상태 스냅샷
- `snapshotId × statId × chgerId` 중복 제거 규칙
- 충전소×수집시각 패널 `station_tick_panel.parquet`
- 5·10·15·30분 도착 가용성 라벨 생성 코드
- 시간 순서 기반 train·valid·test 분할
- 충전소 이력 피처와 D1 정적·준실시간 피처
- SOC 계산기와 도착 SOC 위험 규칙

### 2.2 보완할 부분

- 모델 학습용 단일 정본 데이터셋이 아직 고정되지 않았다.
- 학습과 추론에서 동일한 피처명·타입·null 규칙을 강제하는 계약이 없다.
- 기존 backtest는 `GradientBoostingClassifier`이며 HistGradientBoosting 비교가 없다.
- 일부 실험 코드가 null을 0으로 채워 `미관측`과 `가용 0대`를 혼동할 수 있다.
- 무작위 차량·SOC 시뮬레이션은 실제 학습 피처로 사용할 수 없다.
- 현재 horizon 라벨은 관측 가능한 행만 남으므로 미관측 편향을 별도로 측정해야 한다.

## 3. 모델링 단위 결정

### 3.1 기본안: 충전소 단위

학습행은 다음으로 정의한다.

```text
station_id × feature_as_of × horizon_minutes
```

정답은 `feature_as_of + horizon_minutes` 부근에 해당 충전소에서 사용 가능한 충전기가 1대 이상 관측됐는지 여부다.

충전소 단위를 권장하는 이유:

- 서비스 출력이 충전기 개별 추천이 아니라 충전소 추천이다.
- 현재 충전기 패널은 미관측 비율이 높아 개별 충전기 모델이 불안정하다.
- 가용 충전기 수·전체 충전기 수·다중 충전기 효과를 직접 반영할 수 있다.
- 현재 replay 및 ETA 라벨과 행 단위가 일치한다.

### 3.2 대안: 충전기 단위

DA②가 충전기별 확률을 예측한 뒤 충전소별 확률 합으로 집계하려는 경우에만 별도 분기를 검토한다.

```text
station_id × charger_id × feature_as_of × horizon_minutes
```

충전기 단위는 라벨 커버리지, 상태 유지 가정, 충전기 간 상관관계, 충전소 집계 함수를 추가로 검증해야 한다. 모델 담당자 합의 전에는 구현하지 않는다.

## 4. 학습 데이터 계약 초안

### 4.1 식별·시각·분할

| 필드 | 의미 |
|---|---|
| `station_id` | 충전소 ID |
| `feature_as_of` | 모델 입력이 관측 가능한 기준시각 |
| `horizon_minutes` | 도착까지 남은 시간 |
| `label_observed_at` | 정답을 판정한 미래 관측시각 |
| `split` | `train/valid/test` |
| `source_snapshot_id` | 입력을 만든 AWS 스냅샷 |

### 4.2 기본 피처

| 영역 | 피처 후보 |
|---|---|
| 현재 상태 | `available_count`, `usable_count`, `observed_count` |
| 규모 | `total_charger_count`, `fast_charger_count`, `slow_charger_count` |
| 관측 품질 | `observation_coverage`, `status_age_minutes`, `freshness_flag` |
| 변화 | 최근 가용 대수 변화, 마지막 상태 전환 후 경과시간 |
| 시간 | `hour`, `weekday`, 주말 여부 |
| 과거 이력 | 과거 전용 rolling 가용률, 시간대별 가용률, 세션 지표 |
| 접근성 | 공용 여부, 운영 여부, 좌표 품질 |
| 도착시간 | `horizon_minutes` |

원천 상태 코드, 충전기 유형 등 범주형 피처는 정수의 크기 관계로 오해되지 않도록 명시적으로 인코딩하거나 집계한다. 고유값이 많은 `station_id`는 기본 모델 피처로 직접 넣지 않고 식별·평가 열로 유지한다.

### 4.3 라벨

| 값 | 의미 |
|---|---|
| `1` | 도착시각 부근에 사용 가능한 충전기 1대 이상 관측 |
| `0` | 도착시각 부근 상태를 관측했고 사용 가능 충전기 0대 |
| `null` | 도착시각 부근에 신뢰할 수 있는 관측이 없어 판정 불가 |

`null`을 `0`으로 변환하지 않는다. 라벨 허용 시간 오차와 관측 충전기 최소 개수는 메타데이터에 기록한다.

### 4.4 SOC 처리

사용자 SOC는 충전소의 미래 점유 상태를 만드는 피처가 아니므로 HGB 가용성 학습 데이터에 넣지 않는다.

```text
HGB 출력: 도착 시 충전소 가용 확률
SOC 계산: 해당 사용자가 안전하게 도달 가능한지
DA② 랭킹: 가용 확률 + SOC 위험 + ETA + 거리 + freshness
```

SOC는 요청 시점에 결합하고 예상 도착 SOC 10% 이하 후보를 제외하는 안전 규칙으로 유지한다.

## 5. 피처–타겟 관계 및 유의성 검증

피처가 타겟과 관련 있는지 반드시 점검한다. 다만 모든 피처에 `상관계수 0.5 이상`을 요구하지 않는다.

- Pearson·Spearman·점이연 상관계수의 0.5는 강한 단변량 관계에 가깝지만 필수 기준이 아니다.
- 단일 피처 ROC-AUC의 0.5는 무작위 분류 기준이다. 방향을 보정한 AUC는 0.5보다 커야 하지만, 조금 크다는 이유만으로 실용성이 입증되지는 않는다.
- p-value는 일반적으로 0.05 미만을 참고하지만, 행이 많거나 피처가 많으면 작은 효과도 유의하게 보일 수 있다.
- HGB는 비선형·상호작용 관계를 사용하므로 단변량 상관이 낮은 피처도 조합에서 유용할 수 있다.

따라서 `통계적 유의성 + 효과크기 + 시간 외 성능 기여`를 함께 본다.

### 5.1 검증 단위

유의성 검사는 전체 데이터가 아니라 **train 기간에서만** 수행한다. valid·test는 피처 선택에 사용하지 않는다.

동일 충전소가 여러 시각에 반복되는 패널 데이터이므로 각 행이 서로 독립이라고 가정한 단순 p-value를 최종 근거로 사용하지 않는다. 날짜 또는 충전소 단위 block bootstrap·cluster 기반 신뢰구간으로 안정성을 확인한다.

또한 5·10·15·30분 horizon별 관계를 따로 계산한다. 전체에서는 유효해 보여도 특정 horizon에서 방향이 바뀌는 피처를 확인하기 위해서다.

### 5.2 피처 유형별 검사

| 피처 유형 | 1차 검사 | 효과크기·예측력 |
|---|---|---|
| 연속형·순서형 | 점이연 상관, Spearman | 방향 보정 단일 피처 AUC, mutual information |
| 이진형 | 카이제곱 또는 Fisher exact | 타겟 비율 차이, odds ratio |
| 범주형 | 카이제곱 | Cramér's V, 범주별 타겟 비율 |
| 시간·이력형 | horizon·시간대별 분리 검사 | 날짜 block bootstrap 신뢰구간 |
| 모델 내 기여 | 시간 외 permutation importance | 피처 제거 전후 Brier·LogLoss·PR-AUC 변화 |

결측 자체가 신호일 수 있으므로 `is_missing`과 타겟의 관계도 별도로 검사한다. 단, 결측 발생 원인이 미래 정보나 수집 장애를 대신 나타내는 누출 피처인지 먼저 확인한다.

### 5.3 채택 기준

피처를 다음 세 종류로 분류한다.

| 분류 | 기준 | 처리 |
|---|---|---|
| 필수 도메인 피처 | 현재 가용 대수, 관측 커버리지, 상태 경과시간, horizon 등 | 누출이 없으면 기본 포함 후 ablation 검증 |
| 후보 피처 | 단변량 효과 또는 시간 외 모델 기여가 확인됨 | HGB 비교군에 포함 |
| 제외 피처 | 미래 누출, 정의 불명확, 지나친 결측, 시간별 방향 불안정, 중복 정보 | 제외 또는 보류 |

후보 피처의 판단 기준은 다음을 함께 사용한다.

1. 방향 보정 단일 피처 AUC의 신뢰구간 하한이 0.5를 초과하는가?
2. 다중 검정 보정 후 `q-value < 0.05`인가?
3. 효과크기가 해석 가능한 수준인가?
4. 날짜·horizon별 방향이 안정적인가?
5. 해당 피처를 제거했을 때 시간 외 Brier·LogLoss·PR-AUC가 악화되는가?

단일 상관계수가 0.5 미만이라는 이유만으로 제외하지 않는다. 반대로 상관계수가 높더라도 미래 정보, 타겟의 대리값, 수집 장애 코드처럼 운영 시점에 알 수 없는 피처는 즉시 제외한다.

## 6. HistGradientBoosting 적용 시 데이터 원칙

1. `미관측`과 실제 값 `0`을 구분한다.
2. HistGradientBoosting이 결측치를 처리할 수 있으므로 무조건 `fillna(0)` 하지 않는다.
3. 입력 피처는 반드시 `feature_as_of` 이전 정보만 사용한다.
4. rolling 피처는 해당 행보다 과거 시점만 사용한다.
5. 무작위로 만든 차량·SOC·거리 값은 학습 데이터에 포함하지 않는다.
6. 확률값은 별도 calibration 검증 전까지 보장 확률로 표현하지 않는다.
7. 랜덤 행 분할이 아니라 날짜 기준 시간 분할을 사용한다.
8. 동일 충전소의 미래 행이 과거 학습행 피처 계산에 섞이지 않도록 한다.

| 0. 설계 합의 | 행 단위·라벨·horizon·필수 피처 확정 | DA①·DA② | 30~60분 | 계약 초안 승인 |
| 1. 데이터 프로파일 | 패널·라벨 커버리지와 피처–타겟 관계 측정 | DA① | 0.5~1일 | 품질·유의성 프로파일 생성 |
| 2. 학습 마트 구현 | 공용 학습 데이터셋과 스키마 생성 | DA① | 1일 | 정본·샘플·메타 생성 |
| 3. 데이터 QA | 중복·누출·null·분할 단위 테스트 | DA① | 0.5일 | 필수 검사 FAIL 0 |
| 4. 모델 비교 | HGB와 기준선 시간 분할 평가 | DA② | 0.5~1일 | 비교표와 모델 후보 결정 |
| 5. 추론 정합 | 학습·요청 시점 피처 동일성 검증 | DA①·DA②·백엔드 | 0.5일 | 샘플 추론 계약 통과 |
| 6. 운영 연결 | 모델 로딩·재추천 흐름 연결 | DA②·백엔드 | 별도 협의 | API 통합 테스트 통과 |

예상 작업량은 담당자가 uninterrupted 상태로 작업할 때의 초안이며, 데이터 커버리지 문제나 계약 변경이 있으면 조정한다.

## 9. 설계 합의 체크리스트

DA① 기본안으로 데이터는 생성했지만 다음 항목은 DA② 확인이 필요하다.

- [x] DA① 기본 행 단위를 `충전소`로 구현
- [ ] 단일 HGB에 `horizon_minutes`를 넣을지, horizon별 모델을 만들지 DA② 의견 확인
- [x] 양성은 가용 1대 이상, 음성은 전체 상태 확인 후 0대로 구현
- [ ] DA②가 17개 모델 입력 후보와 보류 피처 확인
- [x] 유의성 기준을 효과크기·AUC·시간 외 기여로 구현
- [x] 부분 관측 0대를 음성으로 변환하지 않도록 구현
- [x] DA① 산출물 파일명과 스키마 v1 고정

권장 기본값:

```text
행 단위 = 충전소 × 기준시각 × horizon
모델 = horizon_minutes를 피처로 넣는 단일 HGB부터 비교
라벨 = 도착 시 사용 가능 충전기 1대 이상
SOC = 모델 외부 하드 필터
분할 = 날짜 기반 시간 분할
```

## 10. 완료 게이트

DA①은 다음 조건을 모두 충족하면 학습 데이터 전달을 완료한 것으로 본다.

- 행 단위와 기준시각이 문서·코드·데이터에서 일치한다.
- 기본키 중복이 0건이다.
- 미래 정보가 입력 피처에 들어간 사례가 0건이다.
- 라벨 `null`이 음성 `0`으로 변환되지 않는다.
- train·valid·test 기간이 겹치지 않는다.
- 모든 피처의 타입·단위·null 의미가 스키마에 존재한다.
- 피처별 유의성·효과크기·horizon 안정성 결과가 존재한다.
- 피처 채택·보류·제외 사유가 기록된다.
- 학습 데이터와 요청 시점 입력의 피처명이 일치한다.
- 데이터 생성 명령과 테스트가 재현 가능하다.
- DA②가 샘플 데이터 로딩과 피처 사용 가능 여부를 확인한다.

모델 성능과 모델 채택, 점수·랭킹·캘리브레이션, 모델 서빙은 DA② 완료 기준이며 DA① 완료 조건에 포함하지 않는다.

## 11. 주요 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 개별 충전소 관측이 드묾 | 라벨 편향·낮은 커버리지 | coverage와 label reason을 별도 제공 |
| 충전기 단위 미관측 과다 | 개별 모델 불안정 | MVP는 충전소 단위 사용 |
| 상태 시각과 수집 시각 혼동 | 미래 누출 | `statUpdatedAt`·`fetchedAt`·`feature_as_of` 분리 |
| null을 0으로 대체 | 미관측을 사용 불가로 오판 | null 유지와 missing flag 제공 |
| 상관계수 0.5를 일괄 적용 | 유용한 비선형·상호작용 피처 제거 | 효과크기·단일 AUC·ablation을 함께 사용 |
| 반복 패널 행을 독립 표본으로 간주 | 과도하게 작은 p-value | 날짜·충전소 block 기반 신뢰구간 |
| 피처 다중 검정 | 우연한 유의성 증가 | Benjamini–Hochberg 방식으로 q-value 관리 |
| 확률 과신 | 사용자에게 보장처럼 노출 | Brier·calibration 검증과 보장 표현 금지 |
| 학습·추론 피처 불일치 | 운영 예측 오류 | 공통 `feature_schema_v1`과 샘플 계약 테스트 |
| 모델별 파이프라인 증가 | 유지보수 중복 | 모델 독립 학습 마트 하나만 관리 |
