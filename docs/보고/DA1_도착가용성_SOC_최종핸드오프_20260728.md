## 1. 결론

현재 충전 가능 여부만으로 추천해서는 서비스 핵심 가치를 충족할 수 없다. 과거 상태를 재현한 결과, 현재 가용 후보 중 **15분 뒤 7.08%가 사용 불가**로 전환됐고 추천 입력 상태는 **15.99%가 변경**됐다.

따라서 신뢰도는 선점 방지 보증값이 아니라 위험을 낮추는 입력이어야 한다. 실제 서비스에는 다음 네 가지가 함께 필요하다.

1. 추천 요청 직전 최신 캐시 상태 확인
2. TMAP ETA와 차량 SOC를 요청 시점에 결합
3. 이동 중 신규 AWS 스냅샷 또는 ETA 변화 감지
4. 주 후보가 위험해지면 재정렬하고 대체 후보 제시

예약·점유 잠금 API가 없으므로 `availability_guaranteed`는 항상 `false`다.

## 3. 도착 시점 가용성 replay

행 단위는 `충전소 × 추천 시점 t0 × 고정 도착시간`이다. 과거 요청별 TMAP ETA가 없으므로 5·10·15·30분 고정 구간으로 재현했으며, 미래 수집 간격을 건너뛰거나 미래 정보를 입력에 사용하지 않았다.

| 도착시간 | 평가 행 | 도착 가용률 | 사용 불가 전환율 | 입력 상태 변경률 | 실패 시 fallback 커버율 |
|---:|---:|---:|---:|---:|---:|
| 5분 | 194,686 | 96.65% | 3.35% | 8.87% | 53.01% |
| 10분 | 190,013 | 96.05% | 3.95% | 10.45% | 52.18% |
| 15분 | 172,516 | 92.92% | 7.08% | 15.99% | 45.90% |
| 30분 | 148,474 | 88.41% | 11.59% | 21.39% | 38.68% |
| 전체 | 705,689 | 93.84% | — | 13.67% | 45.20% |

15분 기준 가용 충전기 수에 따른 차이도 확인됐다.

- 현재 가용 충전기 1개: 도착 가용률 **90.96%**
- 현재 가용 충전기 여러 개: 도착 가용률 **96.75%**

즉 `available_count == 1`은 단순 신뢰도 점수보다 직접적인 재확인·fallback 트리거로 사용하는 편이 타당하다.

fallback은 주 후보에서 직선거리로 가까운 5개 충전소 중 추천 시점과 도착 시점 모두 가용한 후보의 존재 여부다. 실제 서비스에서는 직선거리가 아니라 TMAP 경로시간으로 다시 계산해야 한다.

결과 폴더: [`arrival_availability_replay_20260728`](../data/analysis/arrival_availability_replay_20260728/)

## 4. SOC 검증

차량 마스터 26종과 미등록 차량 fallback, TMAP 15개 경로, 현재 SOC 5개 구간을 조합해 2,025개 시나리오를 계산했다.

| 현재 SOC | 시나리오 | 안전 도착률 | 위험률 | 도달 불가율 |
|---:|---:|---:|---:|---:|
| 10% | 405 | 0.00% | 100.00% | 2.22% |
| 15% | 405 | 83.46% | 16.54% | 0.25% |
| 20% | 405 | 97.78% | 2.22% | 0.00% |
| 30% | 405 | 100.00% | 0.00% | 0.00% |
| 50% | 405 | 100.00% | 0.00% | 0.00% |

운영 규칙은 예상 도착 SOC가 10% 이하면 후보 제외, 10~15%면 가까운 다중 충전기 후보를 우선 검토하는 것이다. 미등록 차량은 50kWh·4.0km/kWh fallback을 사용하되 `SOC_FALLBACK`을 반드시 전달한다.

이 결과는 한 출발지의 15개 경로를 사용한 결정론적 시나리오다. 관측 사용자 SOC 분포나 전체 지역 성능으로 일반화할 수 없다. 현재 BMS 자료도 연속 37km 주행 1건 수준이어서 온도·고도·공조·열화·운전 습관까지 검증했다는 주장은 하지 않는다.

결과 폴더: [`soc_route_scenarios_20260723`](../data/analysis/soc_route_scenarios_20260723/)

## 6. 재추천 트리거 제안

| 조건 | 처리 |
|---|---|
| `available_count <= 0` | 즉시 제외·재정렬 |
| `available_count == 1` | 최신 캐시 재확인·fallback 준비 |
| 상태 관측 15분 초과 또는 미관측 | `CHECK_REQUIRED` |
| 예상 도착 SOC 10% 이하 | 하드 필터 후 재정렬 |
| 예상 도착 SOC 10~15% | 가까운 다중 충전기 후보 우선 |
| ETA 5분 이상 변화 | SOC 재계산·재정렬 |
| 이동 중 신규 AWS 스냅샷 | 주 후보 상태 비교 후 필요 시 재정렬 |

공공 API를 사용자 새로고침마다 호출하지 않는다. AWS 수집 캐시를 사용하고, TMAP은 백엔드가 최종 shortlist에 대해서만 요청 시점에 호출한다.

## 7. 남은 승인과 담당

DA① 구현과 검증 산출물은 완료됐다. 다음은 다른 담당자의 승인·구현 항목이다.

- DA②: freshness·가용 충전기 수·SOC 위험 필드를 점수 또는 하드 필터에 채택
- 백엔드: 요청 시점 TMAP·SOC 결합, 신규 캐시 감지, 재정렬·fallback API 구현
- 프론트엔드: “보장” 표현 금지, 상태 변경·재추천·fallback 안내
- 공통: 계약 승인 후 shared types와 API 계약에 반영

승인 전에는 DA② 추천 코어, 백엔드 API, 공통 타입을 DA①이 임의로 변경하지 않는다.
