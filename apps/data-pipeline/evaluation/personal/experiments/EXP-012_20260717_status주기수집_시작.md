## 0. 왜 하는가 (목적)

지금 데이터로는 **도착 시 가용 라벨·시계열 피처를 만들 수 없다.**  
상태정보가 **단일 시점·커버리지 약 2.34%**뿐이기 때문이다.  
(모델 학습·점수 실험은 AI·데이터 ② — ①은 재료를 쌓는다.)

주기 수집의 목적은 다음과 같다.

| 쌓이는 것 | 나중에 쓰는 곳 |
|---|---|
| 시각별 status 스냅샷 | `available_at_arrival` 라벨 생성 |
| `status_age` 시계열 | 신뢰도·신선도 피처 |
| 15/30/60분 가용률 | P1 피처 |
| 요일·시간대 패턴 | 기준모델·LightGBM 입력 |
| 반복 관측 표본 | Phase B 진입 게이트 (≥4주) |

```text
지금: 규칙 기반 시연 (A-01~A-08) + status 축적
나중: Logistic / LightGBM / CatBoost (라벨·시계열 확보 후)
```

**학습은 하지 않는다. 수집만 한다.**  
“정확도 높은 AI”를 지금 만들기 위한 작업이 아니라, **나중에 학습이 가능해지게 하는 선행 작업**이다.

### API를 다 쓰는가? (한도 계산)

EvCharger **일 1,000 calls** (info+status 합산 보수). 안전 마진 50 → 실사용 목표 ≈ 950.

| 간격 | 하루 회차 | 1회 5 calls 가정 | 일 호출량 | 판정 |
|---|---:|---:|---:|---|
| 5분 | 288 | ×5 | **1,440** | ❌ 한도 초과 위험 |
| **15분 (초기)** | 96 | ×5 | **480** | ✅ 한도 내 |
| 10분 | 144 | ×5 | 720 | △ 여유 적음 |

첫 스냅샷 실측: **493 rows / 5 API calls**.  
따라서 **최종 목표는 5분**이지만, **초기 운영은 15분**으로 시작한다.  
호출량이 안정적으로 1~2 pages로 줄면 **interval**을 다시 검토한다.

### ⚠ interval vs period — 서로 다른 개념

| 구분 | 우리 설정 | 의미 | 누가 정하나 |
|---|---|---|---|
| **interval** | `--interval-minutes 15` | **몇 분마다 API를 호출**해 스냅샷 CSV를 저장할지 | 우리 스케줄러 (`run_loop.py`) |
| **period** | `--period-minutes 20` | **최근 N분 안에 상태가 바뀐 충전기만** API가 돌려줌 | EvCharger `getChargerStatus` 파라미터 |

```text
[우리] 15분마다 호출 (interval)
         ↓
[API]  "지난 20분(period) 동안 statUpdDt가 갱신된 충전기만" 반환
         ↓
[우리]  그 결과를 fetchedAt 시각과 함께 스냅샷 CSV로 저장
```

- `period=20`은 **“20분마다 수집한다”는 뜻이 아니다.**
- `period`는 **변경분(incremental) 조회 창**이다. 전체 25,335대가 매번 오는 게 아니다.
- 그래서 row 수가 수백 건인 것이 정상이고, 커버리지 ~2%처럼 보이는 것과 맞물린다.

**왜 interval=15, period=20?**

| 규칙 | 이유 |
|---|---|
| `period ≥ interval` | 15분마다 돌릴 때, 직전 15분 창만 보면 경계에서 누락 가능 → **period를 조금 더 길게** 잡아 겹침 |
| interval은 한도용 | API calls/일을 줄이려고 **우리가** 15분으로 시작 |
| period는 API용 | 한 번 호출에 **얼마나 넓은 변경분**을 가져올지 |

잘못된 이해 예:

```text
❌ "15분 간격이니까 period도 15" → 같은 개념으로 묶기
❌ "period=20이면 20분마다 수집" → API 주기 아님
✅ "15분마다 호출하고, 매번 최근 20분 변경분을 받는다"
```

메인 `collection/config.py` 주석과 동일한 원칙: **스케줄 간격과 period는 맞추되, period는 interval 이상**이 안전하다.

## ⚠ 수집 주의사항 (최우선 · 위반 금지)

> 본 실험·수집을 시작하기 **전에** 아래 3항을 반드시 지킨다.
> 위반 시 원본 오염·형상관리 충돌·API 차단이 발생한다.

### 1. `docs/data/extracted/` 덮어쓰기 금지

- 원본 extracted CSV는 **읽기 전용**이다.
- 새 status는 **날짜·시각 스냅샷 파일**로만 쌓는다.
- 예: `daegu_charger_status_20260717_134500.csv`
- 기존 `daegu_charger_status_20260716_*.csv` 를 수정·치환하지 않는다.

### 2. 샌드박스 / 별도 수집 경로만 사용

- 산출물·로그·호출 카운터는 **오직**  
  `evaluation/personal/experiments/SANDBOX_20260717_status_periodic_collection/`
- 메인 `apps/data-pipeline/collection/` DB·스케줄러와 **섞지 않는다** (형상관리 꼬임 방지).
- 안정화·검증 후에야 별도 PR로 메인을 이관한다.

### 3. API 호출 한도·장애 대비

- EvCharger **일 트래픽 한도 1,000건/일** (info+status 합산 보수 관리).
- 안전 마진(50) 남기고, 한도 근접 시 **해당 회차 스킵**.
- **초기 운영**: `interval=15분`(우리 호출 주기), `period=20`(API 변경분 창). 둘은 **다른 개념** — 아래 §0 참고.
- 타임아웃·502/504 시 재시도 후 실패 로그, 다음 회차로 진행.
- 다페이지·호출량 증가 시 간격을 더 늘린다.

```text
금지: extracted/ 덮어쓰기 · 메인 collection 경로에 실험 CSV 적재 · 한도 무시 연속 호출
허용: SANDBOX/.../data/snapshots/ 타임스탬프 적재 · 호출 로그 · 스킵
```
